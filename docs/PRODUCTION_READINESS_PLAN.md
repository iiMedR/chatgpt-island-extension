# Public production-readiness plan

Decision: no hosted backend/deployment capability exists. Version 0.9.0 is a controlled local developer preview. The ZIP installs only extension assets; it is not a backend installer or a public service. No infrastructure is deployed in this milestone.

| Priority / owner             | Action                                                                                                                                                                                                                                                               | Acceptance evidence                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| High / maintainer + security | Choose local per-installation secure provisioning or a separately authorized hosted HTTPS service. Define origin/identity, credential rotation/revocation and local threat assumptions. Never embed a shared secret/key in a distributed extension.                  | Threat-model approval and adversarial authorization tests; an exact documented installation flow  |
| High / backend operations    | For a hosted option, implement authenticated user access, per-user limits/quotas, project cost controls, secret management, privacy-preserving monitoring, cancellation and availability ownership.                                                                  | Independent review, misuse/load tests, operating procedures and explicit deployment authorization |

Live calls require separate authorization. | Recorded environment/version/results, real screenshots and a passing hosted CI run                |
| Medium / privacy owner       | Identify operator/contact, review data declarations, provide public policy/support URLs and evaluate loopback HTTP/secure transmission and pre-installation disclosure against current store rules.                                                                  | Human-approved policy/consent/listing, matching actual deployment and data handling               |

Build a new candidate after runtime/backend changes, repeat extraction/hash checks and obtain explicit upload/publish authorization.                                                                      | Signed-off release checklist; no automatic upload/tag/push                                        |

Current backend audit: starts via npm run server:dev or npm --prefix server start after build; configuration is server/.env with OPENAI_API_KEY, OPENAI_MODEL (gpt-4.1-mini example), PORT=8787 and exact EXTENSION_ORIGIN. Key stays server-side. Bind is 127.0.0.1; exact Origin/Host/CORS and application/json are checked. Body cap 256 KiB; selected/current limits 10,000/8,000 UTF-16 units; completed history 20 messages/30,000 units. Four concurrent generations, 25-second backend deadline (worker 28/client 30), abort propagation, code-only errors/logs and no database are implemented. Responses are non-streaming/store:false, output bounded to 2,048 tokens/16,000 units. Cache-Control:no-store applies to accepted-origin responses. There is no local client authentication, per-user rate limiting, total spend cap or provider-retention guarantee. Do not treat the current process as publicly deployable.
